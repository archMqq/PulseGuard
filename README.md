# PulseGuard

**Статус проекта:** Разработка приостановлена на неопределенный срок. Автор сменил профессиональный фокус на развитие в сфере AQA (Automated Quality Assurance). Данный репозиторий заархивирован в его текущем состоянии как демонстрация навыков backend-разработки и проектирования отказоустойчивых высоконагруженных систем.

## О проекте
PulseGuard — это высоконагруженный асинхронный сервис трекинга и менеджмента ошибок, спроектированный как легковесная On-Premise альтернатива Sentry.
Основная задача системы — быстро собирать сырые события об ошибках от клиентских SDK, группировать их в уникальные инциденты на основе алгоритма фингерпринтинга и уведомлять разработчиков о критических всплесках без деградации производительности под нагрузкой.

## Стек технологий
- Язык: Go (Golang)
- Брокер сообщений: Kafka (segmentio/kafka-go)
- Кэш / In-memory БД: Redis (redis/go-redis)
- База данных: PostgreSQL (pgx)
- Инфраструктура: Docker, Docker Compose

## Что было реализовано в рамках MVP

### Архитектура
Проект спроектирован в микросервисной архитектуре. В рамках MVP основной упор был сделан на ядро системы (Highload-пайплайн приема и обработки ошибок). Сервисы Identity и Project были опущены для максимальной фокусировки на производительности Ingestion и Processing слоев.

### 1. Сервис Ingestion
Отвечает за прием сырых логов от клиентов.
- Реализован HTTP-сервер для валидации и приема событий.
- Внедрен внутренний батчинг на базе `kafka.Writer`. Сообщения асинхронно накапливаются во внутренних очередях-батчах в памяти (с учетом партицирования) и отправляются в Kafka, не блокируя HTTP-хендлеры.
- Настроено изолированное структурированное логирование (zap) исключительно для критических инфраструктурных сбоев (защита дискового ввода-вывода от DoS-атак клиентскими ошибками).

### 2. Сервис Processing
Отвечает за вычитывание батчей из Kafka, дедупликацию и сохранение в базу данных.
- **Фингерпринтинг:** Реализован алгоритм генерации уникального отпечатка инцидента на основе комбинации `[Type + Level + File + Method + Line]` из первого кадра стектрейса.
- **Оптимизация работы с Redis:** Внедрен Redis Pipelining для проверки принадлежности событий проектам. Использован `sync.Pool` для переиспользования буферов памяти, чтобы минимизировать аллокации и разгрузить Garbage Collector.
- **Оптимизация записи в PostgreSQL:** - Разделение данных: `error_issue` (уникальные проблемы) и `error_event` (история всех логов).
  - Вставка новых `error_issue` реализована через `pgx.Batch` и SQL-механизм UPSERT (`ON CONFLICT DO NOTHING / RETURNING`). Это переносит разрешение состояния гонки (race conditions) при параллельной работе множества воркеров на сторону СУБД.
  - Вставка сотен сырых логов `error_event` реализована через бинарный протокол `pgx.CopyFrom` (Bulk insert). Это позволяет писать данные напрямую на диск в обход стандартного планировщика запросов Postgres, что кратно повышает пропускную способность.
- **Highload-алертинг:** Разработан асинхронный механизм подсчета ошибок. Использована распределенная блокировка (Debounce) через `SETNX` заглушки в Redis. При превышении порога, сервис не блокирует текущий батч внешними HTTP-вызовами, а формирует событие в топик `system-alerts` для отдельного консьюмера уведомлений.

### 3. Инфраструктура
- Написаны SQL-миграции для PostgreSQL.
- Подготовлена конфигурация Docker Compose для поднятия локального окружения (Kafka, PostgreSQL, Redis, Prometheus).
